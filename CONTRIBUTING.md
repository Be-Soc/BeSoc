# Contributing to besoc

Конвенции, workflow и правила для координационного репозитория
организации Be-Soc. Документ самодостаточен и опирается на правила
ниже: осознанные пины сабмодулей, 100% line coverage для любого
кода организации, newtype для доменных типов, никаких silent
fallbacks.

besoc — небольшой координационный репозиторий: собственного кода
нет, только `LICENSE` (GPLv3), `specs/index.md` (кросс-репо индекс
спецификаций) и четыре git-сабмодуля: `PoSoc/` (набор спецификаций
протокола), `CloDem/` (пока пуст), `quinn/` и `rust-libp2p/`
(форки upstream Rust-проектов). Разработка кода идёт в
субрепозиториях; besoc координирует спецификации и закрепляет
пины. Разделы «Конвенции кода / качества» и «Тесты» — общие для
любого кода, пишущегося в репозиториях организации.

## Git workflow

- **Каждая задача — в worktree.** `git worktree add ../<issue-name>
  -b issue-<name>`. Не коммитьте в `main` напрямую — открывайте
  ветку под issue и PR в `main`.
- **Precommit + build-ok.** Договорились: каждый значимый changeset
  коммитится как `precommit`; после успешного прогона всех проверок
  (для самого besoc — целостность ссылок `specs/index.md` и
  корректность пинов сабмодулей; для кодовых репозиториев — tests +
  lint + fmt) эти `precommit` объединяются в один commit
  `build-ok`. Финальный commit на завершение подзадачи — отдельный,
  с развёрнутым описанием «что и зачем».
- **Не используйте `--force` в `main`.** Для feature-веток force
  с `--force-with-lease` допустим, если вы уверены, что локальная
  история полна.
- **Сообщения коммитов** — в развёрнутом стиле (не «fix bug»),
  объясняющем *почему*, а не *что*. Для bump'ов сабмодулей —
  какой пин, на какой коммит и зачем (см. § «Сабмодули»).

## Сабмодули

Пины сабмодулей (`PoSoc/`, `CloDem/`, `quinn/`, `rust-libp2p/`;
соответствие путей и URL — в `.gitmodules`) — основное содержание
этого репозитория: besoc координирует экосистему через
зафиксированные коммиты. Отсюда правила:

- **Bump пина — осознанное изменение в отдельном коммите.**
  Обновление указателя сабмодуля коммитится отдельным коммитом,
  в сообщении которого — что обновилось и зачем (upstream-релиз,
  протестированный фикс, синхронизация форка с upstream).
- **После bump — перепроверьте `specs/index.md`.** Пути и описания
  в индексе действительны для закреплённых коммитов; после смены
  пина убедитесь, что все ссылки из `specs/index.md` по-прежнему
  резолвятся (файлы существуют, структура каталогов субрепозитория
  не уехала), и при необходимости обновите индекс тем же
  изменением.
- **Никаких коммитов внутри сабмодуля как побочного эффекта.**
  Работа в `PoSoc/`, `quinn/`, `rust-libp2p/` — задачи этих
  репозиториев, со своими ветками и PR. Изменить код сабмодуля
  «между делом» из задачи besoc — ошибка: superrepo фиксирует
  только указатели, контент сабмодуля меняется в нём самом.
- **Пин обязан указывать на запушенный коммит.** Указатель
  сабмодуля в суперрепозитории должен ссылаться на коммит,
  доступный на remote сабмодуля (Be-Soc fork), а не на локальный
  only-коммит — иначе checkout besoc сломается у остальных
  участников (проверка: `git -C <submodule> branch -r --contains
  <pin>` не пуст).

## Конвенции кода / качества

besoc собственного кода не содержит; эти правила действуют для
любого кода в репозиториях организации Be-Soc. Примеры ниже —
в терминах Rust (основной язык экосистемы); для других языков
применяются эквиваленты.

### Архитектурные правила

- **100% line coverage на каждом PR** в кодовые репозитории — гейт
  при мерже (`cargo-llvm-cov --fail-under-lines=100` или
  эквивалент языка).
- **Никаких `unwrap()` / `expect()` / паник в production-коде.**
  Только в тестах и fuzz-harness'ах, где panic — это
  success-path.
- Все error path'ы — **типизированные ошибки** (enum'ы), не строки
  и не паники; конвертация в общую ошибку допустима только на
  краю приложения (CLI, точка входа).
- **Никаких silent fallbacks.** Если значение не распарсилось или
  ответ невалиден — это `Err`, а не ноль/дефолт/пропуск.
- **Newtype для магических и доменных типов.** Никаких голых
  примитивов там, где значение имеет доменный смысл
  (идентификаторы, количества в протокольных единицах и т.п.).
- **Default-константы — single source of truth.** Один модуль
  определяет все дефолты; остальной код читает оттуда, не
  дублирует.
- **`unsafe` (и эквиваленты в других языках) — только явно
  проверенные и задокументированные.** Каждый блок сопровождается
  обоснованием инвариантов и отдельным внимательным ревью; без
  этого — запрещён.
- **Doc-комментарии обязательны для публичных API:**
  - первый абзац — краткое описание (что это, когда звать);
  - второй — контракт (допустимые значения, возвраты, ошибки);
  - третий — edge cases, race conditions, UB.
- Имена: модули snake_case, типы PascalCase, константы
  SCREAMING_SNAKE_CASE.

### Тесты

- Пишутся **вместе с кодом** в каждой подзадаче. Отдельных
  «test phases» нет.
- Структура: unit-тесты — в том же модуле (`#[cfg(test)] mod
  tests` для Rust); integration — **только через публичный API**,
  чистый black-box; внутренние детали тестируются на уровне
  модуля, а не через лазейки в интеграционных тестах.
- **Property-based testing там, где он уместен** (парсинг,
  сериализация, round-trip); число cases — по конфигам в коде.
- **Каждый фикс бага пинается regression-тестом:** после фикса
  добавляется тест с тем входом, который воспроизводил баг.
- **Таймауты на async-тестах** (для Rust — обёртка вида
  `ntest::timeout`, 5 секунд). Deadlock в async-тесте должен
  падать, а не висеть.
- **Тесты полностью оффлайн и детерминированы.** Сети в тестах
  нет (подмены/mocks); источники случайности инжектятся, когда
  тест зависит от выбранного значения.
- **Тесты на парсинг — table-driven.** Каждый случай — отдельный
  тест с явным ожидаемым значением, не один большой `forEach`,
  который флапает и плохо читается в отчёте.

## Quality gates / Code review checklist

- [ ] fmt зелёный (`cargo fmt --all -- --check` или эквивалент
      языка).
- [ ] Lint зелёный с `-D warnings` (`cargo clippy --workspace
      --all-targets -- -D warnings` или эквивалент языка).
- [ ] Тесты зелёные; coverage ≥ 100% lines.
- [ ] Новый публичный API имеет doc-комментарий с контрактом.
- [ ] Никаких `unwrap`/`expect`/паник в production.
- [ ] Никаких `unsafe` без явного аудита и документации.
- [ ] Сообщение коммита объясняет **почему**, не **что**.
- [ ] Изменение поведения сопровождается обновлением затронутых
      спецификаций и/или `specs/index.md` в том же PR — не
      отдельным.
- [ ] Изменения, критичные для безопасности или протокола, —
      **2-reviewer rule**: мерж только с approve от второго
      ревьюера; критичность упомянута в PR description.

## Что НЕ нужно делать

- ❌ Добавлять CI-гейты, которые вы не проверили локально. Если
  добавляете gate — прогоните его локально *точно той же командой*,
  что в CI, на актуальном HEAD. Не доверяйте «должно работать».
- ❌ Подмешивать в фикс посторонние чистки и «улучшения» кода,
  которого задача не касалась: scope = asked, не «пока я тут».
- ❌ Ослаблять guard молча — порог coverage, lint-правило,
  проверку — «чтобы CI прошёл». Ослабление — осознанное
  изменение с обоснованием и ревью, а не быстрый фикс.
- ❌ Обновлять спецификации и код отдельными PR, когда они обязаны
  оставаться консистентными: спека и реализация едут вместе, в
  одном PR.
