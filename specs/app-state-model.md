# Модель состояния приложений: один узел — общее хранилище — много приложений

**Версия:** 0.3 (distribution bundles — один узел на устройство; v0.2 — добавление BeSoc Base App; v0.1 — базовая модель приложений)
**Статус:** черновик / RFC — материал для обсуждения; не является нормативной частью спецификации PoSoc
**База:** спецификация протокола PoSoc v0.13 ([PoSoc/specs](../PoSoc/specs/index.md)), межслойная спецификация «CloDem поверх PoSoc» ([specs/posoc-cdem.md](posoc-cdem.md)); концепция cdem — `CloDem/cdem.md`

**Архитектурное решение (основание версии 0.1).** Все приложения экосистемы Be-Soc на устройстве пользователя синхронизируются через один узел PoSoc и используют общее хранилище состояний. Node Runtime — единый Rust-рантайм узла — владеет единой БД; приложения (CloDem, GplVote, Chat, BeSoc Base App) — домены записей поверх общего транспорта; изоляция доменов и междоменный доступ — через штатные consent/FRIEND/MEMBER_OF-механики PoSoc; синхронизация между устройствами — следствие anti-entropy (LWW + тай-брейк, детерминированная сходимость), а не отдельный механизм. Целевая платформа — только мобильные телефоны Android/iOS; аудитория без серверов: узел сети работает исключительно на устройстве пользователя (Linux-серверы — только вспомогательная bootstrap/relay-инфраструктура сообщества).

**Основание версии 0.2 — BeSoc Base App.** BeSoc — не только невидимый Node Runtime, но и базовое приложение с собственным UI пользовательских механизмов PoSoc (L0/генезис, FRIEND-связи, consent-гранты, ключи, доверие): обычный клиент Local API без привилегий в Node Runtime ([3.5](#asm-3.5)).

**Основание версии 0.3 — distribution bundles.** Единица распространения — bundle: один листинг магазина содержит Node Runtime + BeSoc Base App + выбранные UI-модули доменов; Active Node Runtime на устройстве — ровно один ([3.6](#asm-3.6)). Решение закрывает открытый вопрос v0.2 о размещении нескольких приложений на iOS.

## 1. Назначение и область действия

<a id="asm-1"></a>

Документ фиксирует модель «один узел — общее состояние — много приложений» и отвечает на пять вопросов:

1. **как устроен узел на устройстве** — один Node Runtime, Host-профили Android/iOS, Host-нейтральность ядра ([3](#asm-3));
2. **как приложения разделяют общее хранилище состояний** — домены записей, доменные теги, cross-domain ссылки, изоляция и доступ ([4](#asm-4));
3. **как состояние синхронизируется** — общий транспорт PoSoc, eventual consistency как норма ([5](#asm-5));
4. **каким контрактом приложения связаны с узлом** — Local API ([6](#asm-6));
5. **как модель доставляется пользователю через магазины приложений** — distribution bundles, один узел на устройство ([3.6](#asm-3.6)).

Категории положений:

- **[N]** — нормативное требование модели: обязательное для реализаций слоя приложений Be-Soc;
- **[R]** — рекомендация: желательное, но не обязательное;
- **[P]** — используется PoSoc как есть: механизм v0.13 применяется без изменений.

Область действия — концептуальный уровень модели приложений: состав узла, контракт Local API, жизненный цикл, ресурсы. Форматы Local API, схемы БД, UI — предмет отдельных спецификаций. Документ не изменяет спецификацию PoSoc v0.13: единственная точка стыковки с протоколом — унаследованное требование T1 ([9](#asm-9)).

**Соглашения.** Ссылки `[PRIN-*]`, `[ARCH-*]`, `[L0-*]`, `[HIER-*]`, `[TRUST-*]`, `[DEF-*]`, `[LIM-*]`, `[ZKP-*]`, `[FMT-*]` ведут на разделы спецификации PoSoc v0.13 (пути относительны `specs/`); `[pcd-*]` — на разделы межслойной спецификации [posoc-cdem.md](posoc-cdem.md); «cdem §N» — на разделы исходной концепции `CloDem/cdem.md`.

## 2. Терминология

<a id="asm-2"></a>

| Термин | Определение |
|---|---|
| **Node Runtime** | Единый Rust-рантайм узла PoSoc: транспорт (соцграф, anti-entropy), хранилище, валидация записей; без UI. Единственный носитель сети на устройстве ([3.1](#asm-3.1)). |
| **Host** | Платформенный контейнер Node Runtime: Android — foreground service (отдельный процесс с локальным API), iOS — процесс приложения, ядро in-process (xcframework + uniffi) ([3.2](#asm-3.2)). |
| **Application** | Приложение-потребитель Local API (CloDem, GplVote, Chat, BeSoc Base App); в составе bundle поставляется как UI-модуль ([3.6](#asm-3.6)). |
| **Domain** | Пространство записей приложения в общем хранилище: прикладные записи с доменным тегом, изолированные от других доменов по умолчанию ([4.2](#asm-4.2)). |
| **State Store** | Единая БД узла: идентичность, соцграф, записи всех доменов, производные состояния; владелец — Node Runtime ([4.1](#asm-4.1)). |
| **Local API** | Единый локальный контракт Host↔UI: примитивы query/subscribe/submit/consent-* ([6](#asm-6)); единственный способ доступа приложений к узлу. |
| **Domain Tag** | Префикс типа прикладной записи, разделяющий пространства доменов (T1, [pcd-5](posoc-cdem.md#pcd-5)); например `besoc.cdem`. |
| **Cross-domain link** | Явная ссылка из записи одного домена на запись другого домена ([4.3](#asm-4.3)). |
| **Distribution bundle (bundle)** | Единица распространения: один листинг магазина = Node Runtime + BeSoc Base App + выбранный набор UI-модулей доменов ([3.6](#asm-3.6)). |
| **BeSoc Base App** | Базовое приложение экосистемы с собственным UI пользовательских механизмов PoSoc (L0, FRIEND, consent, ключи, доверие); обычный клиент Local API без привилегий в Node Runtime ([3.5](#asm-3.5)). |

Нотация и термины PoSoc — [GLOS-13](../PoSoc/specs/glossary.md#glos-13).

Соотношение со слоями межслойной спецификации «CloDem поверх PoSoc» (категории [P]/[C]/[I], [pcd-1](posoc-cdem.md#pcd-1)): Node Runtime, State Store и транспорт — слой PoSoc (используется как есть, аналог **[P]**); домены приложений и их производные состояния — механизмы надстройки (аналог **[C]**); Local API, доменные теги и правила изоляции — стыковочные соглашения слоя приложений (аналог **[I]**).

## 3. Архитектура: Node Runtime и Host-профили

<a id="asm-3"></a>

### 3.1 Один Node Runtime

<a id="asm-3.1"></a>

- **[N]** Node Runtime — единственный носитель сети на устройстве: весь PoSoc-транспорт ([ARCH-2.2.1](../PoSoc/specs/implementation/04_node_transport.md#arch-2.2.1), anti-entropy [ARCH-2.2.3](../PoSoc/specs/implementation/04_node_transport.md#arch-2.2.3)), хранилище и валидация записей живут в одном Rust-рантайме. Приложения не участвуют в сети сами по себе — только через узел.
- **[N]** Один узел — одна идентичность: пара ключей $(x, pk)$ ([ARCH-2.1.1](../PoSoc/specs/concept/02_architecture.md#arch-2.1.1)) на устройство; дублирование узла на устройстве запрещено ([3.6](#asm-3.6)).
- **[P]** Узел применяет транспортные правила PoSoc без изменений: валидация подписей, канонической формы и правила будущего ([ARCH-2.4.2](../PoSoc/specs/concept/02_architecture.md#arch-2.4.2)), LWW-разрешение конфликтов ([ARCH-2.4.4](../PoSoc/specs/concept/02_architecture.md#arch-2.4.4)), сходимость в пределе ([ARCH-2.5](../PoSoc/specs/implementation/04_node_transport.md#arch-2.5)).

### 3.2 Host-профили: Android и iOS

<a id="asm-3.2"></a>

- **[N] Android-профиль:** Host — foreground service (отдельный процесс): полноценный фон с оговорками Doze; UI-приложения и UI-модули взаимодействуют с сервисом только через Local API.
- **[N] iOS-профиль:** Host — процесс приложения, ядро in-process (xcframework + uniffi-биндинги): отдельного процесса нет; фон — best effort (BGTask/push), узел онлайн эпизодически — платформенная норма, а не отказ модели ([5.2](#asm-5.2)).

### 3.3 Host-нейтральность ядра

<a id="asm-3.3"></a>

- **[N]** Платформенная логика — только в Host-слое (жизненный цикл процесса, пермишены, фоновые механизмы OS, биндинги языка); в ядре Node Runtime её нет. Ядро не знает, под каким Host-профилем исполняется.
- **[N]** Внутренний контракт ядра узкий: `start`/`stop`/`checkpoint` (жизненный цикл — [7](#asm-7)); всё остальное — Local API поверх ядра, единый для обеих платформ ([6](#asm-6)).
- **[R]** Один и тот же исходник Rust-ядра собирается под оба Host-профиля без ветвления платформенной логики.

### 3.4 Сравнение профилей и следствия для доставки

<a id="asm-3.4"></a>

| Аспект | Android | iOS |
|---|---|---|
| Host | foreground service, отдельный процесс | процесс приложения, ядро in-process |
| Биндинги | uniffi → Kotlin (вызовы к сервису) | uniffi → Swift (прямой вызов) |
| Фон | сервис живёт (оговорки Doze) | замирает; BGTask/push — best effort |
| Присутствие узла в сети | постоянное | эпизодическое — норма ([5.2](#asm-5.2)) |
| Несколько UI | клиентские приложения и UI-модули | только UI-модули одного процесса |
| Разделение Runtime между приложениями | возможно: exported-сервис ([3.6](#asm-3.6)) | невозможно в принципе (sandbox/процессы) |
| Следствие для доставки | bundle — основная модель; exported-сервис — запасная | только bundle ([3.6](#asm-3.6)) |

### 3.5 BeSoc Base App — базовое приложение экосистемы

<a id="asm-3.5"></a>

BeSoc — не только невидимый Node Runtime: экосистеме нужно приложение, в котором живут пользовательские механизмы, требуемые PoSoc на уровне пользователя. Без него приложения-домены (CloDem, GplVote, Chat) не смогут управлять базовыми примитивами сети.

- **[N] Обычный клиент Local API.** BeSoc Base App использует тот же контракт Local API, что и доменные приложения; для Node Runtime он неотличим от любого приложения и не является частью ядра.
- **[N] Без привилегий в Node Runtime.** Явно запрещаются «бэкдорные» интерфейсы ядра, доступные только базовому приложению. Полнота контракта проверяется силами BeSoc Base App: чего не умеет Base App — дыра в контракте ([6.2](#asm-6.2)).
- Состав UI Base App — пользовательские механизмы PoSoc: управление L0/генезисом ([L0-4](../PoSoc/specs/concept/04_l0.md#l0-4)), FRIEND-связи, consent-объекты — выдача/отзыв грантов, включая междоменные ([4.4](#asm-4.4)–[4.5](#asm-4.5)), ключи и key loss ([ARCH-2.3.2](../PoSoc/specs/concept/02_architecture.md#arch-2.3.2); рецепт ротации — [DEF-7.3.3](../PoSoc/specs/concept/07_defenses.md#def-7.3.3)), управление доверием ([TRUST-6.1](../PoSoc/specs/concept/06_trust.md#trust-6.1), [TRUST-6.3](../PoSoc/specs/concept/06_trust.md#trust-6.3)).

### 3.6 Distribution bundles — один узел на устройство

<a id="asm-3.6"></a>

- **[N] Единица распространения — bundle.** Один листинг магазина содержит Node Runtime + BeSoc Base App + выбранный набор UI-модулей доменов (например, «BeSoc + CloDem»). Гарантия «установлен besoc ⇒ установлен clodem» достигается составом пакета (один бинарник), а не зависимостями магазина: App Store и Google Play не поддерживают зависимостей между листингами, а на iOS разделение Node Runtime между приложениями невозможно в принципе (sandbox/процессы).
- **[N] «Установка функции» = активация домена внутри bundle.** Модульность сохраняется на уровне кода и Local API: домены изолированы ([4](#asm-4)); выделение домена в standalone-листинг позже — без изменения модели.
- **[N] Active Node Runtime на устройстве — ровно один.** Все UI-модули bundle живут в его Host-процессе. Второй экземпляр узла на устройстве запрещён: он означал бы дублирование или разделение идентичности — противоречие [3.1](#asm-3.1) и [4.1](#asm-4.1).
- **[N] Bundle — не superapp.** Монолитного UI и общих прикладных прав нет: общие только Runtime и его минимальные пермишены; междоменный доступ — только явные ссылки ([4.3](#asm-4.3)) и домен-гранты ([4.4](#asm-4.4)–[4.5](#asm-4.5)).
- **[R] Android-опция:** при необходимости нескольких пакетов клиентские приложения могут биндиться к exported-сервису core-приложения (только Android); на iOS это невозможно, поэтому bundle — основная и нормативная модель.

## 4. Общее хранилище состояний

<a id="asm-4"></a>

### 4.1 Владелец — Node Runtime

<a id="asm-4.1"></a>

- **[N]** State Store один, владелец — Node Runtime; собственные сетевые хранилища у приложений запрещены. Приложения разделяют состояние через домены, а не через копии.
- **[N]** Единство состояния: одна идентичность ([ARCH-2.1.1](../PoSoc/specs/concept/02_architecture.md#arch-2.1.1)), один соцграф (FRIEND/MEMBER_OF), общие производные состояния (в духе «состояние — чистая функция хранимых записей», [ARCH-2.4.8](../PoSoc/specs/concept/02_architecture.md#arch-2.4.8)).
- **[P]** Записи — формата [FMT-2.8](../PoSoc/specs/implementation/01_records_formats.md#fmt-2.8): канонизация и подписи [FMT-2.7](../PoSoc/specs/implementation/01_records_formats.md#fmt-2.7), классы consent objects/actions — [ARCH-2.3](../PoSoc/specs/concept/02_architecture.md#arch-2.3).

### 4.2 Доменные теги

<a id="asm-4.2"></a>

- **[N]** Каждая прикладная запись несёт доменный тег, разделяющий пространства доменов: требование T1 ([pcd-5](posoc-cdem.md#pcd-5)) открывает пространство прикладных типов записей при закрытом нормативном наборе v0.13 ([FMT-2.8](../PoSoc/specs/implementation/01_records_formats.md#fmt-2.8)).
- **[N]** Правила именования тегов: обратная иерархия сегментов от общего к частному — `besoc.cdem.*`, `gplvote.*`, `besoc.chat.*`; тег закрепляется за доменом; коллизии и сквоттинг исключает реестр тегов (открытый вопрос [10.2](#asm-10)).
- **[P]** Транспорт валидирует подписи, каноническую форму и правило будущего ([ARCH-2.4.2](../PoSoc/specs/concept/02_architecture.md#arch-2.4.2)); семантика payload — за приложением (T1).

### 4.3 Cross-domain ссылки — только явно

<a id="asm-4.3"></a>

- **[N]** Ссылка из записи домена A на запись домена B — только явным указанием (домен + тип + идентификатор); неявное пересечение пространств имён доменов запрещено.
- **[R]** Явность ссылки не означает доступа: чтение чужой записи — только через грант ([4.4](#asm-4.4)).

### 4.4 Изоляция и междоменный доступ

<a id="asm-4.4"></a>

- **[N]** Изоляция по умолчанию: приложение читает и пишет свой домен; доступ к чужому — только через выданный пользователем грант.
- **[N]** Гранты — на штатных механиках PoSoc: FRIEND ([ARCH-2.3](../PoSoc/specs/concept/02_architecture.md#arch-2.3)), MEMBER_OF ([HIER-5.2](../PoSoc/specs/concept/05_hierarchy.md#hier-5.2), [HIER-5.2.1](../PoSoc/specs/concept/05_hierarchy.md#hier-5.2.1)), consent-семантика TTL/автопродление/мгновенный revoke ([ARCH-2.3.1](../PoSoc/specs/concept/02_architecture.md#arch-2.3.1), [ARCH-2.4.5](../PoSoc/specs/concept/02_architecture.md#arch-2.4.5)).
- Выдача и отзыв междоменных грантов — через UI BeSoc Base App ([3.5](#asm-3.5)); пример потребности — перенос согласия cdem в терминах доменов ([pcd-4.2](posoc-cdem.md#pcd-4.2) — фильтры домена читают живость иерархий как предикат, не создавая собственных записей).

### 4.5 Приватность

<a id="asm-4.5"></a>

- **[P]** Сетевой уровень: публичность записей в компоненте связности — принцип PoSoc ([PRIN-1.2.5](../PoSoc/specs/concept/01_intro_principles.md#prin-1.2.5)); тайна содержимого — только roadmap ZKP ([ZKP-11](../PoSoc/specs/concept/11_privacy_zkp.md#zkp-11), [LIM-10.3](../PoSoc/specs/concept/10_limitations.md#lim-10.3)).
- **[N]** Локальный уровень: домен-гранты на устройстве — единственный способ доступа приложения к чужим доменам через Local API; сетевая публичность не отменяет локальный контроль доступа.

## 5. Синхронизация

<a id="asm-5"></a>

### 5.1 Один транспорт на все домены

<a id="asm-5.1"></a>

- **[N]** Все домены реплицируются одним транспортом узла: транспорт = соцграф ([ARCH-2.2.1](../PoSoc/specs/implementation/04_node_transport.md#arch-2.2.1)), обнаружение утаивания — anti-entropy ([ARCH-2.2.3](../PoSoc/specs/implementation/04_node_transport.md#arch-2.2.3)); отдельных каналов или протоколов синхронизации на домен нет.
- **[P]** Конфликты разрешаются LWW по назначению с тай-брейком по $H(\mathrm{record})$ ([ARCH-2.4.4](../PoSoc/specs/concept/02_architecture.md#arch-2.4.4)); согласованность — в пределе ([ARCH-2.5](../PoSoc/specs/implementation/04_node_transport.md#arch-2.5)).
- **[N]** Синхронизация устройств пользователя — следствие anti-entropy (те же записи, тот же транспорт), а не отдельный механизм; мультиустройственность как модель — открытый вопрос ([10.1](#asm-10)).

### 5.2 Эпизодическое присутствие — норма

<a id="asm-5.2"></a>

- **[P]** Согласованность — в пределе, в моменте — субъективные виды ([ARCH-2.5](../PoSoc/specs/implementation/04_node_transport.md#arch-2.5)); отсутствие мгновенной согласованности и гарантированной доставки — ограничения протокола ([LIM-10.9](../PoSoc/specs/concept/10_limitations.md#lim-10.9), [LIM-10.10](../PoSoc/specs/concept/10_limitations.md#lim-10.10)).
- **[N]** Модель принимает эпизодическое присутствие узла (iOS-профиль, [3.2](#asm-3.2)) как норму: eventual consistency для всех доменов; UI обязан показывать локальный вид как субъективный, без обещаний мгновенной общесетевой согласованности.

### 5.3 Relay и bootstrap — вспомогательные

<a id="asm-5.3"></a>

- **[R]** relay/bootstrap-узлы сообщества (Linux-серверы) — вспомогательная инфраструктура доставки для офлайн-эпизодов; relay-политика и пропускная способность — вне спецификации PoSoc ([LIM-10.17](../PoSoc/specs/concept/10_limitations.md#lim-10.17), ср. [pcd-6.7](posoc-cdem.md#pcd-6.7)).
- **[N]** Relay не интерпретирует payload прикладных записей: он видит только транспортные конверты; семантика — за приложениями.

## 6. Local API — единый контракт Host↔UI

<a id="asm-6"></a>

### 6.1 Нормативные требования к контракту

<a id="asm-6.1"></a>

- **[N]** Один IDL: uniffi-биндинги в Kotlin (Android) и Swift (iOS) генерируются из одного определения.
- **[N]** Одинаковая семантика на обеих платформах: различия только в транспорте вызова (IPC к сервису vs прямой вызов in-process), не в поведении.
- **[N]** Асинхронность: все операции неблокирующие; результаты — через completion/канал/поток событий.
- **[N]** Подписка на изменения: контракт поддерживает наблюдение за изменением состояния (домена/записи) без опроса.

### 6.2 Примитивы и полнота контракта

<a id="asm-6.2"></a>

- **[N]** Набор примитивов: `query` (чтение состояния), `subscribe` (подписка на изменения), `submit` (подача подписанной записи домена), `consent-*` (управление грантами: выдача/отзыв/список).
- **[N]** Полнота контракта: всё управление PoSoc-механиками — L0/генезис, FRIEND, consent-гранты (включая междоменные), key loss, управление доверием — выразимо через Local API силами одного BeSoc Base App ([3.5](#asm-3.5)); это критерий проверяемости полноты API.
- Точные форматы и схемы — вне области действия: предмет отдельных спецификаций Local API.

## 7. Жизненный цикл узла

<a id="asm-7"></a>

### 7.1 Старт и стоп

<a id="asm-7.1"></a>

- **[N]** Поддерживаются координированный стоп (сохранение состояния, чекпоинт по контракту ядра [3.3](#asm-3.3)) и внезапный (kill процесса, разряд батареи): оба безопасны для целостности БД.
- Старт: загрузка чекпоинта → применение журнала → anti-entropy добирает расхождения ([5](#asm-5)); отдельных «быстрых путей» запуска модель не требует.

### 7.2 Фон и закрытие

<a id="asm-7.2"></a>

- Android: сервис живёт в фоне — узел остаётся в сети (с оговорками Doze, [3.2](#asm-3.2)).
- iOS: ядро замирает вместе с процессом; при resume узел добирает расхождения anti-entropy ([5.1](#asm-5.1)) — специальных механизмов «догоняющей синхронизации» нет.

### 7.3 Целостность и восстановление

<a id="asm-7.3"></a>

- **[N]** Атомарность: применение записи к БД атомарно; журнал и чекпоинты согласованы между собой.
- **[N]** Инвариант восстановления: после любого стопа состояние узла — детерминированная функция чекпоинта и принятого множества записей (в духе чистоты состояния, [ARCH-2.4.8](../PoSoc/specs/concept/02_architecture.md#arch-2.4.8)).

### 7.4 Миграции доменных схем

<a id="asm-7.4"></a>

- **[N]** Доменные схемы версионируются; миграции backward-совместимы: узел со старой схемой корректно принимает записи новой версии.
- **[N]** Мигрируются только локальные структуры и производные состояния; сетевые записи не переписываются (неотказуемость подписанных записей, [FMT-2.8](../PoSoc/specs/implementation/01_records_formats.md#fmt-2.8)).

## 8. Хранение и ресурсы

<a id="asm-8"></a>

### 8.1 Горизонты хранения

<a id="asm-8.1"></a>

- **[P]** GC-горизонты ([ARCH-2.2.5](../PoSoc/specs/concept/02_architecture.md#arch-2.2.5)) — минимум корректности собственного состояния узла; обязательная зона хранения — записи собственных связей и групп ([ARCH-2.2.4](../PoSoc/specs/concept/02_architecture.md#arch-2.2.4)).
- **[N]** Поверх обязательной зоны — общий ретроспективный буфер: узел хранит историю прикладных записей доменов в пределах бюджета устройства; архивирование прикладных записей — политика домена (ср. [pcd-3.3-c](posoc-cdem.md#pcd-3.3-c)).

### 8.2 Квоты доменов

<a id="asm-8.2"></a>

- **[N]** Домены получают квоты в бюджете устройства; при исчерпании вытеснение идёт из ретроспективного буфера по политике домена; обязательная зона ([ARCH-2.2.4](../PoSoc/specs/concept/02_architecture.md#arch-2.2.4)) вытеснению не подлежит.
- **[R]** Общий лимит State Store настраивается пользователем; домены конкурируют за ретроспективный буфер (взаимодействие квот с живыми consent — открытый вопрос [10.4](#asm-10)).

## 9. Требования к PoSoc

<a id="asm-9"></a>

Единственное требование — унаследованное **T1** «перевозка прикладных записей» ([pcd-5](posoc-cdem.md#pcd-5)): открыть пространство прикладных типов записей с доменным разделением тегов при валидации «подпись + каноническая форма + правило будущего» и семантике payload за приложением.

Обоснование двойной зависимости модели от T1:

1. **перевозка:** прикладные записи всех доменов идут общим транспортом узла ([5.1](#asm-5.1)) — без открытого пространства типов транспорт их не принимает;
2. **доменные теги:** разделение общего хранилища на пространства приложений ([4.2](#asm-4.2)) — без тегов нет изоляции доменов.

Новых требований к PoSoc данный документ не вводит: Host-профили, Local API, bundle-модель, квоты и жизненный цикл — механизмы слоя приложений; платформенное ограничение iOS-фона транспорт уже терпит по построению ([ARCH-2.5](../PoSoc/specs/implementation/04_node_transport.md#arch-2.5), [LIM-10.9](../PoSoc/specs/concept/10_limitations.md#lim-10.9)–[LIM-10.10](../PoSoc/specs/concept/10_limitations.md#lim-10.10)); спецификация T1 — открытая задача в [TODO.md](../TODO.md).

## 10. Открытые вопросы

<a id="asm-10"></a>

1. **Мультиустройственность.** Один пользователь — несколько устройств: одна идентичность на несколько узлов или узел-на-устройство с синхронизацией как следствием anti-entropy ([5.1](#asm-5.1)); пока неспецифицировано.
2. **Реестр доменных тегов.** Кто ведёт реестр `besoc.*` и сторонних тегов, как предотвращать коллизии и сквоттинг ([4.2](#asm-4.2)).
3. **Гранулярность домен-грантов.** Грант на весь домен, на тип записи или на scope внутри домена ([4.4](#asm-4.4)).
4. **Квоты vs живые consent.** Как вытеснение ([8.2](#asm-8.2)) соотносится с записями, на которые есть живые гранты и cross-domain ссылки других доменов.
5. **Семантика subscribe.** Гранулярность событий, границы домена, гарантии порядка при эпизодическом присутствии ([6.1](#asm-6.1)).
6. **iOS-фон.** Какие BGTask/push-механизмы считать допустимыми для Node Runtime; риски отклонения App Store ([3.2](#asm-3.2)).
7. **Backup и перенос.** Перенос узла на новое устройство, экспорт/импорт ключей и хранилища; связь с key loss ([ARCH-2.3.2](../PoSoc/specs/concept/02_architecture.md#arch-2.3.2)).
